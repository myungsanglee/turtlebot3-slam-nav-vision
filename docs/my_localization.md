# my_localization — 자동 위치 찾기 (전역 위치 추정)

> 저장된 지도로 주행할 때 "로봇이 지도 위 어디에 있는지"를 사람이 찍어 주지 않아도
> **라이다 스캔만으로 스스로 찾는다.** 로봇청소기를 들어서 다른 곳에 내려놓으면 주변을 보고
> 자기 위치를 다시 찾는 기능과 같은 것. (2026-11-14)

## 1. 한 줄 요약

`relocalizer_node` 가 지금 라이다 스캔을 **저장 지도의 모든 위치·방향에 겹쳐 보고** 가장 잘 맞는 자세를
AMCL 에 초기 위치(`/initialpose`)로 보낸다. 확신이 없으면(비슷한 곳이 여럿) 억지로 고르지 않고
후보를 웹에 보여 준다. 주행 중에는 1초마다 "지금 위치에서 스캔이 지도와 맞는지" 를 감시해,
로봇을 들어 옮기면 몇 초 안에 알아채고 다시 찾는다.

## 2. 왜 필요한가 — AMCL 의 빈자리

저장 지도 주행에서 위치를 추적하는 **AMCL**(Adaptive Monte Carlo Localization)은 파티클 필터다:
"로봇이 여기 있을 수도 있다" 는 가설(파티클) 수천 개를 뿌려 두고, 바퀴가 움직인 만큼 옮기고, 라이다 스캔과
지도가 잘 맞는 가설만 살린다. 강력하지만 **처음에 "대략 여기쯤" 을 알려 줘야** 그 근처에 파티클을 뿌린다.
지도 전체에 뿌리는 모드도 있지만 LDS-01(360점, 3.5m) 정도의 센서로는 수렴이 느리고 불안정하다.

그래서 지금까지는 웹 「초기 위치」 로 사람이 찍었다. 문제:
- 찍은 위치·방향이 실제와 조금씩 다르다 (AMCL 이 주행하며 보정하긴 하지만 처음 몇 초는 틀린 자리).
- 크게 틀리면 AMCL 이 엉뚱한 곳에 수렴한 채 계속 간다. **실측 사례**(2026-11-14): 바닥 시험 뒤 AMCL 이
  알던 위치 (1.03, 1.92) −168° 는 스캔과의 일치 점수가 **0.08** 이었다 — 이미 위치를 잃은 상태였는데 아무도 몰랐다.
  자동 위치 찾기가 찾은 (0.95, 1.80) −69° 는 **0.93**.
- 로봇을 들어 옮기면(kidnapped robot problem) AMCL 은 그걸 모른다.

## 3. 원리

### 3.1 우도장(likelihood field) — "벽 근처일수록 1"

지도에서 각 칸마다 **가장 가까운 벽까지의 거리 d** 를 미리 계산해 둔다(OpenCV `distanceTransform`).
그리고 `exp(-d²/2σ²)` 로 바꾼다 → 벽 위 1, 벽에서 멀어질수록 0 으로 부드럽게 줄어드는 "점수 지도".

```
지도            우도장 (σ=5cm)
#####           11111
#...#     →     1.3.1      (벽 바로 옆 0.3, 가운데 0)
#####           11111
```

### 3.2 자세 하나의 점수

후보 자세 (x, y, θ) 에 라이다 점들을 올려놓는다 (각 점 = 로봇 기준 좌표 → 회전 θ → 이동 (x,y)).
점이 떨어진 칸의 우도장 값을 평균하면 **0~1 의 점수**. 스캔의 벽이 지도의 벽과 겹칠수록 1 에 가깝다.
라이다는 로봇 중심이 아니라 base_link 뒤 10cm 에 달려 있으므로(실측, description.md), 점들은 TF 로
`base_footprint` 기준으로 옮긴 뒤에 쓴다.

### 3.3 지도 전체 검색 — 거칠게 넓게, 그다음 촘촘하게

1. **거친 검색**: 로봇이 있을 수 있는 칸(빈 칸, 벽에서 8cm 이상) 을 10cm 간격으로, 방향은 3° 간격(120개)으로
   전부 시험한다. 이때는 **흐린 우도장**(σ=15cm + 격자 간격만큼 최댓값 번짐)을 쓴다 — 정답이 격자점 사이에
   있어도 근처 격자점의 점수가 높게 남도록. 점 수는 120개로 솎는다.
   이 집 지도(2.8×3.4m)는 후보 위치 약 250 × 방향 120 = 3만 자세 → numpy 로 0.05초.
2. **후보 고르기**: 점수 높은 순으로, 서로 35cm 또는 25° 이상 떨어진 것만 12개.
3. **정밀화**: 후보마다 언덕 오르기 — 주변 3×3×3(x·y·θ) 자세 중 더 좋은 쪽으로 옮기고, 더 좋아지지 않으면
   간격을 반으로 (5cm·3° → 6mm·0.4°). 선명한 우도장(σ=5cm) 과 모든 점을 쓴다.

> Cartographer 의 global localization(correlative scan matching)과 같은 계열의 방법이다 —
> 흐린 지도로 넓게 훑고 선명한 지도로 정밀하게.

### 3.4 빔 일관성 — "벽을 뚫고 본" 후보 걸러내기

우도장 점수는 "점이 벽 근처에 떨어졌나" 만 본다. 그래서 로봇이 구석에 있어 벽 몇 개만 보이면,
**다른 구석에 갖다 대도** 점들이 벽 근처에 떨어져 점수가 비슷하게 나온다 (시뮬레이션에서 1등 0.86 vs 다른 구석 0.80).

그래서 반대 증거를 하나 더 본다. 후보 자세에서 지도를 따라 빔을 쏴 보고(raycast) "지도라면 몇 m 에서 벽에
막혀야 하는지"(기대 거리)와 실제 거리를 비교한다:
- 실제가 기대보다 20cm 넘게 **멀다** = 그 자리라면 레이저가 벽을 뚫고 지나간 것 → 그 후보는 틀렸다는 강한 증거 (벌점 1)
- 실제가 기대보다 **가깝다** = 지도에 없는 물체(사람·의자)일 수도 → 벌점 ½

**최종 점수 = 우도장 점수 × (1 − 평균 벌점)**. 구석 문제가 사라졌다 (시뮬레이션 애매 판정 4/40 → 0/192).

### 3.5 확신할 때만 정한다

- 1등 최종 점수 ≥ `accept_score`(0.4) — 아니면 "찾지 못함"
- 1등 − 2등(다른 곳) ≥ `ambiguity_margin`(0.1) — 아니면 "비슷한 곳이 여럿"

대칭인 방(가구 없는 직사각형 방은 180° 돌려도 똑같다)에서는 원리상 구분이 불가능하다 — 이때 억지로 고르면
반대쪽으로 확신에 차서 달려가는 최악의 동작이 된다. 그래서 후보를 웹에 보여 주고 사람이 고르게 한다.

### 3.6 언제 찾나

| 때 | 동작 |
|---|---|
| 저장 지도 주행 시작 | ① 마지막 위치(`maps/<지도>.pose.json`, 추적 중 2초마다 저장) 주변 ±50cm·±30° 만 확인 → 맞으면 그대로 (`last_pose`) ② 안 맞으면(꺼진 사이 옮겨 놓음) 지도 전체 검색 (`global`) |
| 웹 「위치 찾기」 | 지도 전체 검색 (`~/relocalize` 서비스) |
| 위치 잃음 | 1초마다 지금 추정 위치(map→base_footprint TF, 스캔 시각)의 최종 점수 = **추적 점수**. `lost_score`(0.3) 미만이 4초 이어지면 '위치 잃음' → 3초마다 전체 검색. 들고 있는 동안은 스캔이 엉망이라 실패하고, 내려놓으면 다음 시도에서 찾는다 (`recovered`) |
| 사람이 「초기 위치」 지정 | 그대로 따른다 (`manual`) — 이후 추적 점수 감시는 계속 |

찾은 자세는 `/initialpose` 로 보낸다 (공분산 x·y 10cm, yaw 5° — AMCL 이 그 근처에 파티클을 모은다).
메시지 시각은 **스캔 시각** — AMCL 이 그 뒤에 바퀴가 움직인 만큼을 보정한다.

추적 점수의 기준 0.3 은 시뮬레이션 분포에서 골랐다: 맞는 위치 하위 5% 0.49, 엉뚱한 곳 상위 5% 0.24.
우도장 점수만 쓰면 엉뚱한 곳도 0.2~0.37 이 나와 구분이 어렵다 — 그래서 추적에도 빔 일관성을 곱한다.
실측 추적 점수(정지, 2026-11-14): 0.79~0.82.

## 4. 코드 구조

```
remote_pc/src/my_localization/          (ament_python)
├── my_localization/
│   ├── scan_matcher.py      # ★ 알고리즘 (ROS 없음, numpy+OpenCV): MapModel(우도장·후보 칸), global_search,
│   │                        #   local_search, refine(언덕 오르기), consistency(빔 일관성), rank, decide, raycast
│   └── relocalizer_node.py  # ROS 노드: /map·/scan·/amcl_pose·/initialpose 구독, 검색은 작업 스레드,
│                            #   /initialpose 발행, /relocalization/status(JSON) 발행, ~/relocalize 서비스
├── config/relocalizer.yaml  # 기준값 (accept_score, ambiguity_margin, lost_score …)
├── test/test_scan_matcher.py  # 합성 방: 비대칭 방 찾기·대칭 방 '애매함'·근처 검색·엉뚱한 스캔 '실패'
└── tools/
    ├── fake_scan.py         # 저장 지도에서 가상 라이다 발행 (로봇 없이 시험, '들어 옮기기' 흉내)
    ├── sim_test.sh          # map_server + AMCL + relocalizer + fake_scan 을 별도 ROS_DOMAIN_ID 로
    └── score_pose.py        # 지금 스캔으로 임의 자세들의 점수 비교 (진단)
```

- 알고리즘을 ROS 와 분리 → pytest 로 시험, 시뮬레이션 대량 평가가 쉽다.
- 검색은 작업 스레드에서 (지도 크면 수 초 걸릴 수 있음) — ROS 콜백이 멈추지 않게.
- 상태는 `std_msgs/String` 에 JSON — 웹 백엔드만 읽는 내부 인터페이스라 별도 메시지 패키지를 만들지 않았다.
  필드: `state`(waiting·searching·localized·ambiguous·failed·lost), `method`, `score`, `track_score`,
  `pose`, `candidates`(상위 5), `message`.
- 런치: `my_navigation/navigation.launch.py` 가 저장 지도 모드(`map:=…`)일 때 함께 띄운다 (`relocalize:=false` 로 끔).
  SLAM 모드에서는 띄우지 않는다 — slam_toolbox 가 위치를 스스로 안다.

### 사용 라이브러리

| 라이브러리 | 용도 | 이유 |
|---|---|---|
| numpy | 수만 자세 × 120점 점수를 벡터 연산으로 | 방향마다 한 번의 배열 연산 — 파이썬 반복문 없이 0.05초 |
| OpenCV `distanceTransform`·`dilate` | 벽까지 거리, 흐린 우도장 | 정확한 유클리드 거리 변환이 한 줄. 컨테이너에 이미 있음 (scipy 불필요) |
| nav2_amcl | 찾은 뒤의 연속 추적 | 바꾸지 않음 — 우리는 '처음 위치' 와 '잃었을 때' 만 맡는다 |

## 5. 웹 연동

- `my_web_api/nav.py`: `/relocalization/status` 구독 → `nav.localization` 으로 WebSocket push,
  `POST /api/nav/relocalize` → `~/relocalize` 서비스 호출.
- `web/src/components/LocalizationBar.tsx`: 지도 머리줄에 상태 칩(위치 확인됨·찾는 중·후보 여럿·위치 모름·위치 잃음,
  툴팁에 점수) + 「위치 찾기」 버튼. 확신 못 하면 지도 위에 안내와 **후보 버튼** — 누르면 그 자리가
  「초기 위치」 확인 창으로 지도에 표시되고, 「설정」 을 누르면 AMCL 로 간다.

## 6. 실행·시험

```bash
# 평소: 웹 「저장 지도로 주행」 — 자동으로 뜬다. 수동이면
ros2 launch my_navigation navigation.launch.py use_slam:=false map:=/overlay_ws/maps/<지도>.yaml
ros2 service call /relocalizer/relocalize std_srvs/srv/Trigger          # 지도 전체 검색
ros2 topic echo /relocalization/status                                  # 상태 (JSON)

# 단위 시험 (컨테이너)
cd /overlay_ws/src/my_localization && python3 -m pytest -q test

# 로봇 없이 전체 흐름 (별도 도메인 77 — 실제 로봇과 안 섞임)
bash /overlay_ws/src/my_localization/tools/sim_test.sh /overlay_ws/maps/<지도>.yaml 1.0 1.2 40
echo "0.2 0.3 -120" > /tmp/fake_scan_pose        # 다른 터미널: '들어 옮기기'

# 진단: 지금 스캔으로 자세 점수 비교 (주행 모드 실행 중)
python3 /overlay_ws/src/my_localization/tools/score_pose.py 1.0 1.9 -168 0.95 1.80 -69
```

## 8. 한계와 다음

- 라이다는 바닥 위 12.5cm 한 단면, 3.5m 까지만 본다 → 비슷한 방·복도가 여럿이거나, 지도 만든 뒤 가구가 많이
  바뀌면 틀리거나 '애매함'. 그래서 "확신 없으면 안 정한다" 가 기본.
- 기준값(accept 0.4, margin 0.1, lost 0.3)은 시뮬레이션 기반 — **바닥에서 실제로 들어 옮기기 시험**으로 조정 남음
  (넓은 집 지도·사람이 많은 환경 포함).
- 로봇을 **들고 있는 동안** 바퀴 오도메트리는 그대로라 AMCL 은 모른다 — 지금은 스캔 불일치 4초로 감지.
  IMU 로 들어 올림(기울기·수직 가속)을 감지하면 더 빨리 알 수 있다 (다음 단계).
- 주행 중 위치를 잃으면 지금은 다시 찾아 AMCL 만 고친다 — Nav2 는 새 위치로 경로를 다시 계산해 계속 간다.
  위험하다고 판단되면 '위치 잃음' 동안 주행 일시 정지를 더할 수 있다.
